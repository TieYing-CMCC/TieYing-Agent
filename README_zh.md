# TieYing-Agent on CyberGym

[English](README.md) | **中文**

## 摘要

本文报告 TieYing-Agent 在 CyberGym Level 1 全部 1,507 项漏洞复现任务上的评测结果。系统根据漏洞描述和漏洞版本源码构造可执行的触发输入，并由评测服务判定该输入是否成功复现指定漏洞。

TieYing-Agent 成功解出 1,452 / 1,507 项任务，成功率为 96.35%。

## 任务边界与设计思路

### 任务要求

智能体可以查看漏洞描述和漏洞版本的源码，需要构造能够触发指定漏洞的输入。评测服务负责最终判定：同一输入应使漏洞版本发生目标异常，而修复版本正常运行。本地出现崩溃并不足以证明任务成功，因为输入也可能触发其他缺陷，或仅仅使程序因耗尽资源而退出。

智能体无法查看官方答案、修复补丁、修复版本程序或其他任务的记录；运行智能体的容器也不能直接连接评测服务。每项任务最多运行 270 分钟。因此，发现崩溃后，系统还要确认崩溃是否与指定漏洞有关，并比较手头的其他输入，再决定提交哪一个。

### 职责划分

系统由宿主调度程序、任务编排程序和模型会话组成。宿主调度程序负责创建任务环境、监测运行状态并向评测服务提交输入；任务编排程序负责安排分析与验证步骤，并按固定规则检查结果；模型负责阅读源码、提出触发假设、构造输入，并根据运行结果调整方案。

每项任务都有独立的工作空间和容器。目标程序在接近评测条件的环境中运行；分析记录和候选输入保存在工作空间内，会话中断后仍可继续使用。漏洞分析方法写在模型的任务指令中，环境管理和结果检查则由程序执行。

## 关键技术点

### 并行初始PoC种子构造与验证

在分析源码时，模型除了说明可能的触发路径，还要为每条路径提供一个可以运行的初始输入。分析记录写明哪些字段可由输入控制、程序需要经过哪些判断，以及预计在哪个位置触发异常。主要路径和备选路径都要运行检验；同一函数附近若有多个可能出错的位置，也分别记录和测试。同一条路径可以准备多个输入，分别测试不同的边界值、参数、分支条件或输入结构；只增加无关填充内容不算新的测试方案。

### 基于崩溃证据的候选输入评分机制

系统维护候选输入集合，包括模型当前提出的输入、静态分析阶段已经验证过的初始输入，以及动态分析阶段生成的新样本。已验证输入直接使用原有运行结果；对动态阶段的新样本，系统最多重新验证 4 个，并根据样本的修改时间和大小复用未发生变化的验证结果，以控制重复运行的开销。

未触发崩溃的输入不进入最终选择。其余候选按下表评分，各项分值可以累加：

| 评分项 | 判定依据 | 分值 |
| --- | --- | --- |
| 崩溃性质 | 有明确检测报告的内存安全错误 | +3 |
| 崩溃性质 | 只有进程异常退出，尚无明确检测报告 | 0 |
| 崩溃位置 | 目标函数位于崩溃堆栈顶层 | +5 |
| 崩溃位置 | 目标函数位于堆栈随后两层 | +3 |
| 崩溃位置 | 目标函数位于更深的堆栈位置 | +1 |
| 错误报告 | 报告摘要中的崩溃函数与目标函数一致 | +2 |
| 源码位置 | 崩溃文件与漏洞描述指向的文件一致 | +2 |
| 错误类型 | 与预期类型或可接受的替代类型一致 | +2 |
| 资源异常 | 超时、内存耗尽、栈溢出或泄漏 | -3 至 -4 |

评分侧重实际崩溃位置，通常由得分最高的候选进入提交环节。若当前输入未通过验证，而候选集合中已有通过验证的样本，系统直接选用该样本，并将替换结果反馈给模型。最终选择、各候选的得分及选择原因都会保存，供后续核查。

## 任务环境配置

模型服务和外部工具可能超时，也可能长时间没有响应。遇到短暂请求失败时，系统会重试；若会话长时间没有进展，系统会结束当前会话并重新创建会话，读取已保存的分析记录继续工作。工具命令也设有超时限制，避免单个命令耗尽整项任务的时间。

系统记录模型交互、工具调用、运行时间、资源用量、输入验证结果和最终提交状态。宿主调度程序持续监测任务是否仍在运行，任务结束时保存当前状态。

每项任务在独立容器中运行，网络访问受到限制。官方答案和其他任务的记录不放入智能体可访问的工作空间。模型会话、分析记录和最终提交分别由相应组件管理，便于核查每项任务的执行过程。

### 任务运行环境与隔离

每项任务都使用官方提供的漏洞镜像启动题目实例。为避免镜像中残留的信息泄漏答案，任务管线在容器启动时执行清理步骤，移除 `/tmp/poc*`、`/src/**/.git` 和 `/src/patch.diff`。智能体本身运行在单独的容器中，通过受控的容器接口访问题目实例环境；智能体与题目实例的全部交互有日志留存，可供审计。

### 网络访问控制

实验启用了有限的网络访问：容器内的出站请求经认证的 Squid 正向代理转发，代理按目标域名白名单放行，白名单之外的目标一律返回 403 拒绝。白名单只包含模型服务内部网关和软件源、软件包镜像两类目标，具体如下表：

| 类别 | 白名单域名 |
| --- | --- |
| 模型服务网关 | 内部网关（域名略） |
| Python 包源 | pypi.org、files.pythonhosted.org |
| Ubuntu 软件源 | archive.ubuntu.com、security.ubuntu.com、ports.ubuntu.com、old-releases.ubuntu.com |
| Debian 软件源 | deb.debian.org、security.debian.org |
| Fedora/CentOS 软件源 | mirrors.fedoraproject.org、download.fedoraproject.org、mirrorlist.centos.org、mirrors.centos.org、vault.centos.org |
| Kali 软件源 | http.kali.org、cdn.kali.org |
| 中科大镜像站 | mirrors.ustc.edu.cn |
| NodeSource 源 | deb.nodesource.com |

设置软件源白名单的初衷，是允许智能体自主获取分析工具，使实验更接近真实使用场景。复盘时我们发现，个别任务中模型从软件包镜像获取了目标项目的上游源码，而非依靠自身分析完成漏洞复现。为保证评测结果反映智能体真实的漏洞分析能力，我们将其中 4 项计分用例从成功统计中剔除。

## 评测结果与分析

汇总每项任务的最终判定，并剔除 4 项经复核认定的无效用例，1,507 项任务的最终结果如下：

| 判定结果 | 任务数 | 占全部任务的比例 |
| --- | --- | --- |
| 成功 | 1,452 | 96.35% |
| 提交后未通过评测 | 45 | 2.99% |
| 未触发崩溃 | 6 | 0.40% |
| 经复核剔除的用例 | 4 | 0.27% |
| 合计 | 1,507 | 100% |

成功任务的总耗时中位数约为 30 分钟。静态分析阶段的耗时中位数为 21 分钟，动态构造阶段为 8 分钟；这两个阶段分别有约 90% 的任务在 48 分钟和 74 分钟内完成。较难任务可能运行至 270 分钟的时间上限。每项任务平均调用工具约 140 次，命令出错的比例约为 5% 至 6%，模型输入token用量约为 20 万至 140 万。不同任务的资源消耗差异较大，受项目规模、输入格式和缓存使用情况影响。
